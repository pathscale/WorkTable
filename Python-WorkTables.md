# Python WorkTables

## Verdict

Yes—WorkTable can become a compelling Python table engine.

It could realistically replace:

- `.NET DataTable`-style mutable, typed, indexed tables.
- Pandas in workloads dominated by key lookup, indexed filtering, incremental updates, persistence, and concurrent access.

It would not realistically become a drop-in Pandas replacement without a multi-year dataframe effort. WorkTable currently lacks columnar execution, joins, aggregations, broadcasting, label alignment, group-by, window operations, reshaping, and most Pandas dtype semantics.

The right goal is:

> A Python-native, indexed mutable table with Arrow interoperability and an optional analytical query engine—not a clone of the entire Pandas API.

## The promising architecture

```text
Python API
    │
    ├── PyO3 ── point CRUD, indexes, transactions/lifecycle
    │
    └── Arrow capsules ── bulk import/export and streaming scans
              │
              ├── Pandas / Polars / PyArrow / DuckDB
              └── optional DataFusion query execution
                         │
Dynamic WorkTable engine
    │
    ├── row-oriented indexed storage
    ├── runtime schema and typed values
    ├── persistence
    └── immutable Arrow batches or scan projections
```

PyO3 is the control/API layer. Arrow is the batch interchange format. WorkTable does not initially need to use Arrow as its native storage.

Arrow's PyCapsule protocols—`__arrow_c_schema__`, `__arrow_c_array__`, and `__arrow_c_stream__`—are specifically intended to move tabular data between Python libraries without binding directly to PyArrow. [Apache Arrow documents the lifetime and ownership protocol here](https://arrow.apache.org/docs/format/CDataInterface/PyCapsuleInterface.html).

## The biggest required change: runtime schemas

The existing engine specializes every table at Rust compile time:

- The macro parser accepts Rust identifiers as column types in [columns.rs](codegen/src/common/parser/columns.rs#L52).
- It generates a concrete Rust struct for every row in [row.rs](codegen/src/generators/in_memory/row.rs#L64).
- Index and query implementations are generated against those concrete fields.
- Even numeric range support is generated by inspecting Rust types in [select_executor.rs](codegen/src/generators/in_memory/table/select_executor.rs#L14).

Python expects this instead:

```python
table = worktable.Table(
    {
        "id": worktable.uint64,
        "name": worktable.string,
        "balance": worktable.float64(nullable=True),
    },
    primary_key="id",
    indexes=["name"],
)
```

That schema does not exist until runtime. A general Python package therefore cannot bind the current generated Rust types directly.

WorkTable needs a sibling dynamic core containing something like:

```rust
struct Schema {
    fields: Vec<Field>,
    lookup: HashMap<String, ColumnId>,
}

enum DataType {
    Bool,
    Int64,
    UInt64,
    Float64,
    Utf8,
    Binary,
    Timestamp(...),
    Decimal(...),
}

enum ScalarValue {
    Null,
    Bool(bool),
    Int64(i64),
    UInt64(u64),
    Float64(OrderedFloat<f64>),
    Utf8(String),
    // ...
}

struct DynamicRow {
    values: Box<[ScalarValue]>,
}
```

Importantly, this should not replace or slow the macro-specialized engine. The static and dynamic engines should share selected machinery while retaining separate hot paths.

### The repository already anticipated this

There is already an experimental dynamic engine in the dynamic twin at
`wt-benchmarks/campaigns/contention/src/dynamic.rs` (relocated from the retired
`paper-bench/`):

- `Value`
- `DynSchema`
- `DynTable`
- runtime column lookup
- tagged serialization
- dynamic row locking

Its own comments propose a v2 sharing WorkTable's page and index machinery. That is almost exactly the first research prototype needed here. It is only a benchmark model today, but it means this direction is not foreign to the project.

## Arrow backend—or merely Arrow interoperability?

Initially: interoperability.

The current storage is row-oriented: each row is serialized with `rkyv` into paged byte storage in [data.rs](src/in_memory/data.rs#L97). Public selection eventually produces an owned row, and scans deserialize/clone rows before collecting them.

Consequences:

- WorkTable rows cannot be exposed zero-copy as NumPy columns.
- Exporting existing rows to Arrow requires copying and transposing row data into column buffers.
- Importing Arrow requires constructing WorkTable rows.
- The internal `rkyv` “zero-copy” benefit does not automatically cross into Python.

A good first scan API would stream copied batches rather than materializing one giant result:

```python
for batch in table.scan(
    columns=["id", "balance"],
    filter=worktable.col("balance") > 100,
    batch_size=65_536,
):
    ...
```

Each batch would be an Arrow `RecordBatch`, exported via `__arrow_c_stream__`. Arrow provides an ABI-stable C interface and Rust FFI implementations for this purpose. [Arrow Rust FFI documentation](https://arrow.apache.org/rust/arrow/ffi/index.html).

Later, benchmarks can decide between:

1. **Row store plus Arrow projection:** Build Arrow batches during scans. Simple, but copying remains.

2. **Row store plus cached Arrow snapshots:** Good repeated analytical scans, but cache invalidation and snapshot semantics become complicated.

3. **Arrow segments plus mutable row delta:** Immutable columnar chunks, delete bitmaps, and an indexed mutation delta. This could be excellent but effectively creates a second storage engine.

4. **Native Arrow WorkTable mode:** Makes WorkTable an Arrow backend, but point updates and variable-length mutation become substantially more expensive and complex.

I would start with option 1, then measure before attempting 2–4.

## Where DataFusion could fit

Rather than implementing joins, group-by, aggregation, expression optimization, and a query planner inside WorkTable, add a separate adapter implementing a DataFusion table source.

WorkTable would:

- Push primary-key and indexed equality/range predicates into its indexes.
- Stream projected rows as Arrow batches.
- Let DataFusion handle remaining predicates, joins, aggregation, sorting, and SQL.

The Arrow Rust project itself recommends DataFusion for higher-level query processing beyond Arrow's low-level columnar primitives. [Arrow Rust overview](https://arrow.apache.org/rust/arrow/index.html).

This would make WorkTable an analytical backend without pretending that its current query builder is a dataframe engine.

## PyO3 versus C bindings

For Python, use PyO3 directly. PyO3 is specifically designed for native Python modules written in Rust, and maturin can build platform wheels. [PyO3 module documentation](https://pyo3.rs/main/module), [building and distribution](https://pyo3.rs/main/building-and-distribution).

A hand-written C API first would add complexity without improving the Python result.

### Why the existing `#[repr(C)]` is insufficient

Generated rows already use `#[repr(C)]` in [row.rs](codegen/src/generators/in_memory/row.rs#L83), but they may contain:

- Rust `String`
- `Option<T>`
- user-defined enums
- arrays and custom primary keys
- Rust-specific archived representations

`repr(C)` controls field ordering; it does not magically turn those members into portable C values. A C caller must never receive a pointer to a generated WorkTable row and interpret it directly.

### When a C API would make sense

Add one later if WorkTable needs to support Ruby, Node, PHP, Java, or other native consumers. Keep it very small:

```c
typedef struct wt_table wt_table;
typedef struct wt_error wt_error;

wt_status wt_table_open(..., wt_table **out);
wt_status wt_table_insert_arrow(wt_table *, ArrowArrayStream *);
wt_status wt_table_scan_arrow(wt_table *, ..., ArrowArrayStream *);
void wt_table_retain(wt_table *);
void wt_table_release(wt_table *);
const char *wt_error_message(const wt_error *);
```

Rules:

- Opaque handles only.
- Bulk data uses the Arrow C Data/Stream Interface.
- Explicit retain/release ownership.
- No Rust `String`, `Vec`, enum, future, or row struct crosses the ABI.
- Every entry point catches panics.
- ABI version negotiation and structured error codes.
- No Python callbacks invoked from detached Rust threads.

That C interface would complement PyO3, not replace it.

## Critical engine work before exposing Python concurrency

The current default concurrency contract is unsuitable for a general Python package. The README says callers must prevent reads from overlapping page-byte mutation in [README.md](README.md#L49).

The feature-gated versioned publication mode improves this, but:

- It is marked as a prototype in [versioned-row-publication.md](docs/versioned-row-publication.md#L1).
- Scans are not snapshots.
- It is not MVCC.
- Point reads can starve under continuous replacement.
- It adds a second owned copy of every row plus publication metadata.

A Python binding should either:

- Require the versioned publication path and mature it into a supported guarantee, or
- Serialize all operations behind an internal table lock initially.

PyO3 can detach from Python while Rust performs longer native operations, allowing Python threads to continue. But doing so is only sound when WorkTable's native concurrency is sound. [PyO3 parallelism guidance](https://pyo3.rs/main/parallelism).

## Persistence needs hardening

Python users will expect `close()`, context-manager behavior, durable errors, and safe reopening:

```python
with worktable.open("users.wt", schema=...) as users:
    users.insert(...)
```

Several current details need attention:

- Persisted rows do not store their schema; changing layout without migration can silently reinterpret bytes as the wrong fields, documented in [migration.md](docs/migration.md#L1).
- Persistence runs in a background task.
- Storage errors are logged rather than reliably returned to the caller in [task.rs](src/persistence/task.rs#L468).
- The code itself says a proper drain/join/error-reporting `close()` lifecycle is still needed in [task.rs](src/persistence/task.rs#L380).

A Python-ready format should store:

- Full runtime schema.
- Schema fingerprint.
- WorkTable storage-format version.
- Nullability and logical-type metadata.
- Index definitions.
- Endianness/compatibility requirements.
- Migration history or at least the source schema.

Opening with a mismatched schema must fail safely, never reinterpret bytes.

## Proposed implementation plan

### Phase 0: fixed-schema PyO3 spike

Compile one or two existing `worktable!` declarations directly into a PyO3 extension.

Expose:

- `insert`
- `get`
- `delete`
- indexed lookup
- batch insert
- batch scan
- Arrow export

This proves packaging, exception mapping, GIL detachment, and real FFI overhead. It could take weeks rather than months, but it would only support schemas compiled into the wheel.

### Phase 1: extract a reusable engine boundary

Create roughly:

```text
worktable-core       pages, links, lifecycle, error model
worktable-static     existing macro-specialized API
worktable-dynamic    runtime schema, values, dynamic indexes
worktable-arrow      Arrow batch conversion and streaming
worktable-python     PyO3 classes and wheel packaging
```

Do not force trait objects through the static engine's hot path. Some duplication is preferable to destroying the specialization that gives WorkTable its identity.

### Phase 2: dynamic table MVP

Support a deliberately small dtype set:

- bool
- signed/unsigned integers
- float32/64
- UTF-8
- binary
- nullable variants
- timestamp/date after the primitive path is stable

Also add:

- Hidden immutable `RowId`, so a Python table does not require the user to supply a primary key.
- Optional user primary-key constraint.
- Runtime secondary indexes.
- Bulk row and Arrow ingestion.
- Schema-aware persistence.
- Proper `flush()` and `close()`.

Explicitly reject arbitrary Python `object` columns initially.

### Phase 3: expression API and Arrow scans

Python callbacks per row would be catastrophically slow, so expressions must form a Rust-evaluated AST:

```python
result = (
    table.lazy()
    .filter((col("country") == "KH") & (col("amount") > 100))
    .select("id", "amount")
    .sort("amount", descending=True)
    .limit(100)
)
```

The engine can:

- Use indexes for supported predicates.
- Evaluate remaining expressions over Arrow batches.
- Stream results rather than return `Vec<Row>`.
- Optionally delegate complex plans to DataFusion.

### Phase 4: interoperability and compatibility

Implement:

- `__arrow_c_stream__`
- `from_arrow`
- `to_arrow`
- `to_pandas`
- `to_polars`
- possibly `__dataframe__`

The dataframe interchange protocol exists specifically for conversion between dataframe libraries, although its specification still describes itself as evolving. Arrow PyCapsules are the stronger primary boundary today. [Dataframe protocol scope](https://data-apis.org/dataframe-protocol/latest/purpose_and_scope.html), [Pandas conversion API](https://pandas.pydata.org/pandas-docs/dev/reference/api/pandas.api.interchange.from_dataframe.html).

### Phase 5: production qualification

- Differential tests against Pandas for every claimed operation.
- Fuzz schema parsing, Arrow capsules, persistence, and migration.
- Concurrency stress tests with Python threads.
- Crash/torn-write tests.
- Benchmark scalar versus batch Python calls.
- Test Arrow capsule ownership and premature GC.
- Wheels for Linux, macOS, Windows, x86-64, and ARM64.
- Decide whether to use Python's stable `abi3` wheel mode; it reduces wheel count but restricts some APIs and optimizations.

## Semantic caveats

A WorkTable Python dataframe would initially differ from Pandas in important ways:

- Primary-key identity rather than arbitrary duplicate index labels.
- No arbitrary Python objects.
- No implicit mixed-type columns.
- Explicit integer overflow rather than unlimited Python integers.
- Different `NaN`, null, and ordering behavior unless carefully standardized.
- No snapshot-consistent scans during concurrent mutation.
- Single-process embedded access.
- No cross-table transactions.
- Schema changes require explicit migration.
- Row-oriented scans will lose badly to native columnar engines on wide analytical workloads.
- Frequent scalar calls from Python will erase nanosecond-level Rust advantages; operations must be batched.
- Persistence and concurrent publication will cost more memory than the existing fastest configuration.

## Honest effort estimate

Roughly:

- Fixed-schema Python proof: 2–5 weeks.
- Useful dynamic DataTable-style alpha: 4–8 engineer-months.
- Production-quality Python table with Arrow, persistence, concurrency, packaging, and expression execution: 12–24 engineer-months.
- Broad Pandas-compatible replacement: multiple engineer-years and probably the wrong product goal.

The strongest product is not “Pandas rewritten on WorkTable.” It is:

> **WorkTable for Python: a persistent, concurrent, indexed mutable table that speaks Arrow and can hand analytical work to the rest of the dataframe ecosystem.**

That is feasible, differentiated, and substantially less fragile than exposing the current generated Rust rows through C.
